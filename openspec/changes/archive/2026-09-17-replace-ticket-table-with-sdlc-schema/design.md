## Context

See proposal.md — Why. The relevant current state:

- The only table is `workshop_ai_platform.example.data_tiket_it`: seven columns, every one requiring escaping, contents undesigned.
- It lives in the Jakarta workspace (`dbc-86b2f2e8-b955`), reachable from the agent only through the managed SQL MCP server. The agent's service principal holds `SELECT, MODIFY, CREATE TABLE` on the schema — **not ownership**, so it cannot rename or drop.
- A valid CLI profile `jakarta-workshop` points at that host. A second profile named `jakarta` points at a *different* host and is invalid; it is a trap, not an alternative.
- `agent_server/prompts/system_prompt.md` names the table and its columns, and is read once at import.
- Downstream evaluation work will derive ground truth by querying this table, so whatever is true of the data becomes a contract.

## Goals / Non-Goals

**Goals:**
- A dataset whose interesting properties are *designed and recorded*, not discovered after the fact.
- Reproducibility: the table can be regenerated byte-identically, so ground truth can be refreshed rather than re-derived by hand.
- A migration whose destructive step is deferred and separately confirmed.

**Non-Goals:**
- No application code changes. Tools, routes, serving, and tracing are untouched.
- No Unity Catalog Volume. The wiki that supplies resolution targets is a separate change; until it lands, adherence questions simply have no answer, which the specs already require.
- Not a general-purpose ITSM model. This dataset exists to teach; realism serves that and stops where it stops.

## Decisions

### 1. A new table, not an alteration

All seven existing column names change, fifteen columns are added, and every row is rewritten. `ALTER TABLE` would be a fiction. `CREATE TABLE workshop_ai_platform.example.sdlc_tickets` and leave the original untouched until the new one is verified.

*Alternative considered.* Renaming columns in place and backfilling. Rejected: it produces an intermediate state where the table matches neither the old spec nor the new one, and the system prompt cannot describe it correctly during the window.

### 2. One table spanning planned and unplanned work

`ticket_type` discriminates Bug / Story / Task (planned delivery) from Incident / Service Request / Change (unplanned operations). `sprint` is populated for planned work and absent for unplanned.

This is what makes the capacity-split question answerable, and it is how real trackers model work. The alternative — two tables, or a service-desk-only model — forecloses the most valuable question in the dataset for no gain.

### 3. The schema

```
IDENTITY
  ticket_id                    STRING      NOT NULL      TKT-10423
  ticket_type                  STRING      Bug|Story|Task|Incident|Service Request|Change
  title                        STRING      Bahasa Indonesia
  project                      STRING
WORKFLOW
  status                       STRING      New|In Progress|Blocked|In Review|Done|Cancelled
  status_category              STRING      To Do|In Progress|Done
  priority                     STRING      P1|P2|P3|P4
  severity                     STRING      NULL except Bug|Incident
  resolution                   STRING      NULL until done
PEOPLE
  reported_by                  STRING      NOT NULL
  assigned_to                  STRING      NULL when unassigned
PLANNING
  sprint                       STRING      NULL for unplanned work
  story_points                 DOUBLE      NULL for Bug|Incident
  component                    STRING
  labels                       STRING      comma-separated
TIME
  created_at                   TIMESTAMP   NOT NULL
  updated_at                   TIMESTAMP   NOT NULL
  started_at                   TIMESTAMP   NULL until work begins
  closed_at                    TIMESTAMP   NULL until done
  due_date                     DATE        NULL often
  cycle_time_hours             DOUBLE      NULL until done
CARRIED-OVER CUSTOM FIELDS  (the hostile minority)
  `Custom Field (Root Cause)`  STRING      NULL except Bug|Incident; Bahasa
  `Time Spent (hours)`         DOUBLE      NULL
  `Env/Region`                 STRING
```

Twenty-four columns is deliberate: at seven, an agent can guess a schema; at twenty-four it must run `DESCRIBE TABLE`. `status_category` is derivable from `status` and is kept precisely because redundancy invites inconsistency — see defect D4.

### 4. Exactly three hostile identifiers, framed as carried-over custom fields

Spaces, parentheses, and a slash, confined to three columns that are plausibly legacy. This preserves the escaping lesson while modelling a table a competent engineer would design: a conformed core with unconverted edges.

*Alternative considered.* All-clean naming. Rejected: it silently voids the escaping instruction in the system prompt and the escaping requirement in `cross-workspace-sql`, leaving dead text in both. *Also considered:* keeping every column hostile, as today. Rejected: it teaches reflexive escaping rather than schema inspection, and the reflex is the wrong habit.

**This decision has a storage-format cost, discovered during implementation.** Delta refuses ` ,;{}()\n\t=` in column names unless name-based column mapping is enabled, so the table must be created with `delta.columnMapping.mode = 'name'`. The existing `data_tiket_it` already carries exactly that property for exactly this reason. The consequence to be aware of is that column mapping raises the table's reader and writer protocol versions, so an old external client could fail to read it — irrelevant here, since the only reader is the managed SQL MCP server, but it is the kind of thing that is cheap to know and expensive to rediscover.

### 5. Language follows provenance

Tool-generated fields in English, human-entered fields in Bahasa Indonesia. This is what an English-configured tracker used by an Indonesian team actually produces. It keeps every enumerated value stable and gradeable while making the free text authentic, and it creates a genuine output-language decision for the agent's instructions rather than a cosmetic one.

### 6. Three timestamps, and a duration that covers only the working interval

`created_at` → `started_at` is waiting; `started_at` → `closed_at` is working. `cycle_time_hours` measures the second only.

This is the single most consequential schema decision. A dataset with one end-to-end duration cannot express the most common real finding in delivery analytics — that waiting dominates working — and therefore cannot produce the failure mode where a reasonable-looking query yields a confidently wrong characterisation.

### 7. Planted findings, with recorded magnitudes and verifying queries

Each is verifiable by a query committed alongside the generator.

| | Finding | Magnitude |
|---|---|---|
| F1 | Waiting dominates working | median wait ≈ 19 d, median cycle ≈ 2 d |
| F2 | Unplanned work consumes a large share of effort | ≈ 35 % of recorded time spent |
| F3 | P2 bugs exceed a five-day working target | median cycle ≈ 6.5 d for P2 Bug |
| F4 | Estimation carries no signal | 3-point and 5-point Stories have indistinguishable cycle time |
| F5 | One component dominates defects | ≈ 40 % of Bugs in one component |
| F6 | Throughput dips at Idul Fitri and spikes at month end | ≈ 2× cycle time in the Idul Fitri fortnight |
| F7 | Closures concentrate on one individual | ≈ 22 % of closures on one `assigned_to` |

F3 is answerable only once a target is supplied from outside the dataset, which is the point: until the wiki exists, the correct answer to an adherence question is that the target is unknown.

F7 is reportable in aggregate without naming anyone, which is why the concentration is planted at a magnitude worth reporting — a privacy rule that costs nothing teaches nothing.

### 8. Planted defects, with recorded counts

| | Defect | Rows |
|---|---|---|
| D1 | `closed_at` earlier than `created_at` | 8 |
| D2 | `cycle_time_hours` present while status is not a closed status | 12 |
| D3 | status is `Done` but `resolution` is absent | 15 |
| D4 | `status_category` disagrees with `status` | 5 |
| D5 | `assigned_to` case and whitespace variants of one person | ≈ 315 (45 % of the hero's rows) |
| D6 | `story_points` present on Incident rows | ≈ 10 |

D5 is the important one: it makes a naive aggregation of F7 *silently wrong* rather than erroneous. Every other defect announces itself under validation; D5 only shows up if you look for it.

Its magnitude is a share rather than a row count, and that is a correction made during implementation. At the 30 rows first specified, the defect was present but inconsequential — the naive share came out at 22.3 % against a true 23.3 %, and the concentrated individual still ranked first by a wide margin, so nothing was misread. A defect that cannot change a reader's conclusion does not teach the lesson it was planted for. At 45 % of the hero's rows the naive share falls to about 13 % against a true 23 %, which is a conclusion a reviewer would act on and get wrong. The generator asserts the understatement rather than the count, so the property is what is protected.

### 9. Deterministic generation from a committed script

A script in `scripts/` generates rows from a pinned seed. Indonesian names come from a **name list committed in the script**; **distributions are hand-specified, not sampled freely**, because pure randomness washes out every planted finding.

The script is committed so the dataset is reproducible from source and its planted properties are auditable rather than asserted. This matters directly for the downstream evaluation work: ground truth refreshes by regenerating and re-running the verifying queries.

*Alternative considered.* Spark + Faker on serverless, per the synthetic-data guidance. Rejected as the primary path for a ~4,000-row table: it adds a compute dependency and makes exact planted magnitudes harder to guarantee than a deterministic single-process generator. *Faker itself was also rejected as the name source*: it would either ship into the deployed application or need a dependency group of its own, and its locale output changes between versions — which defeats the reproducibility this decision exists to provide. A committed list is auditable and pinned by construction.

### 10. Volume and window

≈ 4,000 rows over 18 months, ≈ 220/month. Large enough for monthly and quarterly aggregates to be stable, small enough to query cheaply and to eyeball in full.

### 11. Rename before dropping, and run DDL as a human

Step one is `ALTER TABLE data_tiket_it RENAME TO data_tiket_it_deprecated`. It breaks every reference immediately — which proves nothing still depends on it — while staying instantly reversible. The drop is a separate, later, confirmed step.

DDL runs under the `jakarta-workshop` profile, not the app's service principal: rename and drop require ownership, which the principal was deliberately not granted.

## Risks / Trade-offs

- **Random generation washes out the planted findings** → distributions are hand-specified and every finding has a verifying query that is run as an acceptance step, not assumed. This is the primary failure mode of this change.
- **Ground truth is derived before the findings are confirmed** → the downstream evaluation change is explicitly blocked until the verifying queries have been run against real rows. Deriving expected values from unverified data is the one mistake here that is expensive to undo.
- **The window between creating the table and updating the prompt** → during it the agent describes a table that is no longer the target. Mitigated by ordering: create and verify, then update the prompt, then rename the old table.
- **Dropping `data_tiket_it` is effectively irreversible after `VACUUM` retention (7 days)** → deferred out of this change entirely; the rename is what this change performs.
- **Planted defects make the table look broken to anyone unaware of them** → they are recorded in the spec and in the generator, and the table description carries a note that defects are intentional.
- **Several workshop participants writing to the schema concurrently under one service principal** → unchanged from the existing accepted consequence in `cross-workspace-sql`; participants can still collide on derived table names. Not addressed here.
- **D5's whitespace variants could be read as a generation bug** → the generator names it explicitly and the count is recorded.

## Migration Plan

1. Identify the Jakarta compute that will execute DDL and DML — the managed MCP SQL server is serverless, but a statement endpoint or warehouse id is needed for the loader. Verify before generating anything.
2. Commit the generator and its verifying queries.
3. Create `sdlc_tickets` and load the generated rows.
4. Run every verifying query for F1–F7 and every detecting query for D1–D6; record actual magnitudes.
5. Update `system_prompt.md` for the new table, columns, and the narrowed escaping rule.
6. Confirm the agent answers a question over `sdlc_tickets` end to end.
7. `ALTER TABLE data_tiket_it RENAME TO data_tiket_it_deprecated`.
8. Confirm nothing broke; the agent still answers from `sdlc_tickets`.

**Rollback.** Before step 7, drop `sdlc_tickets` and revert the prompt — the original table was never touched. After step 7, rename it back. Nothing in this change is destructive to reverse.

## Open Questions

- Whether `data_tiket_it_deprecated` is dropped after the first workshop run or retained as a comparison artifact. Does not affect this change's specs, approach, or tasks.
- Whether row volume should grow for later cohorts. 4,000 is a starting point; the generator makes the count a parameter, so revisiting is cheap.
